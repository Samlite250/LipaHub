# Remaining implementation phases

The current real-account milestone adds private support requests and admin replies (`004_member_support.sql`), member balance-correction history and production demo gating. Follow [LIVE_SETUP.md](LIVE_SETUP.md) to connect a new Supabase project. Live database, email and hosting validation remain pending.

The local implementation now includes the member frontend, Express API, configurable Supabase Auth, user/content CRUD administration, published member resources, announcements and support settings. See SYSTEM_ADMIN.md for setup and verification limits. It does not complete Phases 2–5 of the master brief.

1. **Phase 2 — service workflows.** Replace planned states with genuine voucher, deposit, client payment, ranks, withdrawal, bonus, referral, history, support, course and task workflows. Confirm providers, product rules, currencies, eligibility, content and external destinations. Never let a client report its own successful payment.
2. **Phase 3 — original admin panel.** The admin console now matches the member theme and supplies user CRUD, resource/announcement CRUD, system settings, audit records and payment-proof review. Remaining work includes broader analytics, moderation and live integration validation. Require server-verified RBAC and audit trails for every privileged action. Add user verification, payment review, moderation, support and configuration workflows. User metadata must never grant roles.
3. **Phase 4 — schema and secure APIs.** Add reviewed migrations, RLS, immutable double-entry ledger, currency-safe amounts, idempotency, payment-event signature verification, provider reconciliation, withdrawal state machine, vouchers, referral attribution, reward eligibility, support, notifications, audit logs and approved configuration. Test cross-user access and concurrent balance changes. No arbitrary balance edits or fabricated receipts. Financial history must come from the ledger.
4. **Production integrations.** Supabase setup and real email delivery, provider sandbox testing, privacy/terms and operator contact, domain ownership, hosting configuration, accessibility review and translation review. Keep trading simulation-only until authorized integrations, risk controls and required reviews are approved. Chat rewards require real eligibility, moderation and anti-abuse checks.
5. **Phase 5 — full QA.** Phase 1 browser checks cover current functionality. Extend to real auth, RLS, payment verification, idempotency, RBAC and failure recovery as later features are implemented. Capture new screenshots after each material UI change.

No production accounts, cloud projects, provider registrations, domains, database migrations or deployments have been created by this local milestone.

The local audit/backend milestone adds a testable API factory, shared authentication and configuration validation, dependency readiness, bulk payment settings, request tracing, bounded HTTP requests, proof failure recovery, embedded PostgreSQL tests and migration 007 for fresh payment authorization. See SYSTEM_AUDIT.md and BACKEND.md. These changes prepare integration; they do not complete the live/provider phases above.

A local-only manual-review withdrawal state machine (migration 013, `WITHDRAWAL_REQUESTS_ENABLED`) now holds, cancels, rejects and pays wallet funds with idempotent, versioned RPCs. It has not been applied to the live project, no payout provider is connected, and only the main wallet channel is funded.
