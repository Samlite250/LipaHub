# Invited registration

The dashboard invite card offers the username-based `/register?ref=Cynthia` URL and a compact `/i/<code>` URL, with copy and social-sharing actions. On non-Rwanda dashboards, the card is available from **Invite & Earn** under Accounts; Rwanda members also see it on the dashboard home page. Previously shared `/i/<code>` and UUID links remain supported. The short code uses the first eight base64url characters of the username's SHA-256 hash after trimming and lowercasing; the browser resolves it to the canonical username URL. Previously shared `/?ref=Cynthia` links now open registration directly instead of the landing page. Spaces and other URL characters are encoded automatically. Registration shows the inviter's username above the fields, with `Invited by:` in English and `Ufashijwe na:` in Kinyarwanda.

The invite card reads the latest saved Auth profile, so sessions from before the username migration do not keep showing an account ID. Names with 2–80 characters starting with a letter or number and containing letters, numbers, spaces, periods, underscores, apostrophes or hyphens can be shared directly. Missing or unsupported usernames show a profile prompt instead of substituting an account-ID link. The invite survives home, login, legal-page visits and reloads in the same browser tab for up to seven days. A new explicit `ref` replaces it; a malformed explicit reference clears it. Successful registration clears the saved browser invitation. Ordinary registration without an invitation keeps its existing layout.

`GET /api/invitations/:reference` resolves an existing active Auth account by username, case-insensitively, or by a legacy UUID. Its public response contains only the internal account ID and public username/name, capped at 80 characters. It never returns email, phone, account role or private metadata. Missing, suspended and ambiguous duplicate usernames return 404; configuration or upstream errors return 503. Existing API rate limits and no-store headers apply. Invalid links and service outages do not prevent ordinary registration; transient errors offer retry.

Signup saves the registration `username` separately from `display_name`. It includes the original username reference as `invitation_reference` and, when the inviter lookup succeeds, `invited_by_username` plus the internal account ID in `invited_by`. Migration 014 resolves the original reference on the server and writes an immutable member-to-inviter record with a snapshot of the member's country selected at signup; it also backfills prior validated invitation references. Editable user metadata does not determine the referral tree, country classification or activation status. The authenticated Team page displays three levels. A non-Rwanda member is Active only after a robot activation payment is verified by an administrator. A Rwanda member is Active only after the account activation payment is approved by an administrator. Pending or rejected payments remain Inactive. Referral tracking does not add commissions or rewards.

Existing installations must apply `009_invitation_usernames.sql`, `010_short_invitation_codes.sql` and `014_member_referrals.sql` once, in migration order. The first preserves registration names as usernames; the second adds the short-code resolver, exposed through `GET /api/invitations/code/:code`; the last stores referrals and exposes the private referral query to the backend service role. Username and code lookup functions are also service-role-only. They do not create or delete accounts, change passwords or grant administration. Duplicate names and short-code collisions return no result rather than selecting an arbitrary identity. Codes are case-sensitive, public invitation identifiers; they do not authenticate anyone. Readiness checks the referral table and query alongside the invitation lookups and schema revision 9.

Database tests cover invitation backfill, three-level referral traversal, self-referral rejection and the Rwanda/non-Rwanda activation rules. API and browser checks cover authentication, copy behavior, both languages, persistence through home/login routes, invalid references, escaped display names and mobile overflow. Existing share/copy and authentication checks remain applicable.
