# Invited registration

Members share `/register?ref=Cynthia` or the alternative `/?ref=Cynthia` from their dashboard, using their saved registration username. Spaces and other URL characters are encoded automatically. Registration shows the inviter's username above the fields, with `Invited by:` in English and `Ufashijwe na:` in Kinyarwanda. It uses LipaHub branding and the supplied reference's pale banner and wider desktop card. Previously shared UUID links remain supported.

The invite card displays the username explicitly above its links and reads the latest saved Auth profile, so sessions from before the username migration do not keep showing an account ID. Names with 2–80 characters starting with a letter or number and containing letters, numbers, spaces, periods, underscores, apostrophes or hyphens can be shared directly. Missing or unsupported usernames show a profile prompt instead of substituting an account-ID link. Previously shared account-ID URLs still resolve. The invite survives home, login, legal-page visits and reloads in the same browser tab for up to seven days. A new explicit `ref` replaces it; a malformed explicit reference clears it. Successful registration clears the saved browser invitation. Ordinary registration without an invitation keeps its existing layout.

`GET /api/invitations/:reference` resolves an existing active Auth account by username, case-insensitively, or by a legacy UUID. Its public response contains only the internal account ID and public username/name, capped at 80 characters. It never returns email, phone, account role or private metadata. Missing, suspended and ambiguous duplicate usernames return 404; configuration or upstream errors return 503. Existing API rate limits and no-store headers apply. Invalid links and service outages do not prevent ordinary registration; transient errors offer retry.

Signup saves the registration `username` separately from `display_name`. It includes the original username reference as `invitation_reference` and, when the inviter lookup succeeds, `invited_by_username` plus the internal account ID in `invited_by`. These fields preserve the registration's invitation context. User metadata is editable and must not authorize access or determine rewards, activation or payouts. No trusted referral ledger, team counts, commissions or rewards are implemented by this change.

Existing installations must apply `009_invitation_usernames.sql` once. It preserves existing registration names as usernames and grants its lookup function only to the backend service role. It does not create or delete accounts, change passwords or grant administration. Duplicate legacy names are left ambiguous rather than assigning someone else's identity. Readiness checks the lookup function alongside core schema revision 8. The lookup reads the managed Auth table without changing its ownership or indexes.

Browser checks cover both languages, persistence through the home/login routes, retry, invalid references, escaped display names and mobile overflow. API checks cover response privacy, suspended/missing accounts and safe upstream errors. Existing share/copy and authentication checks remain applicable.
